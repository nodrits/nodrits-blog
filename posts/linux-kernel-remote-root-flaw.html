Critical Linux Kernel Flaw Opens Remote Root Access on Servers

October 31, 2026 · Nodrits Solutions · 4 min read

A critical flaw in the Linux kernel — the code at the heart of millions of servers — can let an attacker with no login at all run commands as root, the highest level of control on a machine. Tracked as CVE-2026-98432, it scores 9.8 out of 10 for severity, and the working exploit was built by an AI model.

What happened

The flaw is a use-after-free bug in the kernel's IPv4 TCP networking code, caused by a race condition in how the kernel handles TCP connection requests. In plain terms, two parts of the kernel can touch the same piece of connection memory at once, and one of them can end up reading memory that has already been freed. Anthropic researchers demonstrated the full chain: leak kernel memory, bypass KASLR (the protection that hides where key kernel code sits), hijack the kernel's control flow, and run an attacker-chosen command as root — all against a server running a Multipath TCP (MPTCP) listener. Their proof of concept took about 53 minutes from the first leak to root command execution.

MPTCP lets one connection use several network paths at once, such as Wi-Fi and mobile data. On Linux, applications must explicitly request it — except that since Go 1.24, Go programs enable MPTCP by default for the sockets they listen on, so some Go-based services may be running MPTCP listeners without their administrators knowing. The flaw affects Linux kernels dating back to version 4.4, including widely used distributions such as Ubuntu, Red Hat Enterprise Linux (RHEL) and Rocky Linux. It does not affect macOS, which uses Apple's XNU kernel rather than the Linux kernel.

There is an honest disagreement about how bad this is. The Linux kernel's own CVE team rates it 9.8, while Red Hat rates it 5.9, treating it as a potential denial-of-service issue because exploiting the race is complex. Anthropic's demonstration is what tips it toward the serious end: the race can be won, repeatedly, until it works. As of October 30, there were no confirmed reports of the flaw being exploited in the wild, and it had not appeared in CISA's Known Exploited Vulnerabilities catalog.

Why it matters

Linux runs a huge share of the internet's servers, cloud instances and network appliances, so a remote-root flaw in its networking code is about as broad as vulnerabilities get. The attack needs no password, no clicked link and no user interaction — just a reachable service. And the exploit itself is a milestone: an unreleased Claude research model found the bug and built the attack, showing that AI can now do end-to-end vulnerability research on the world's most widely deployed software. That cuts both ways — defenders get faster discovery, but so does everyone else.

"The flaw was patched upstream and backported to all maintained stable kernel branches." — Anthropic, on the fix status

The patch picture is uneven. Fixed upstream kernels include 5.10.272, 5.15.223, 6.6.159, 6.1.190, 6.12.113, 6.18.56, 7.2.10 and 7.3-rc7, and Debian, Oracle Linux, Amazon Linux and SUSE have shipped fixes for some versions. But as of October 30, Ubuntu (22.04, 24.04, 26.04 and 26.10) still had kernel fixes in progress, and RHEL 8, 9 and 10 were listed as affected with fixes planned. Until your distribution ships its update, the exposure stays open.

What it means for you

If you run Linux servers, check your kernel version and your distribution's security advisory now, and install the updated kernel package as soon as it lands. Check whether your servers run MPTCP listeners — especially Go-based services, where MPTCP may be on by default. For Go programs, the Go Security Team says setting GODEBUG=multipathtcp=0 disables MPTCP at runtime, but warns that turning it off program by program is fragile: a single exposed MPTCP listener still leaves a system vulnerable. While patches are pending, restrict server access to trusted networks and IP addresses, and consider firewall rules that block IPv4 TCP packets carrying IP options before they reach the vulnerable code. Note that disabling MPTCP alone is not enough, because the underlying flaw can also be triggered through ordinary TCP traffic.

For businesses that don't manage servers directly, the action is simpler: ask your hosting provider or IT team whether your systems are patched, and confirm it in writing. A flaw this broad is exactly the kind that gets swept into automated scanning within days of disclosure.
