GitLab Patches a Maximum-Severity Flaw That Hid for 12 Years

October 23, 2026 · Nodrits Solutions · 3 min read

A single bug report could have handed attackers the keys to thousands of codebases. On Oct 21, 2026, GitLab released emergency patches for CVE-2026-110264 — a maximum-severity CVSS 10.0 flaw that had been hiding in its code for 12 years.

What happened

The bug is an integer overflow in GitLab's Regular Expression Compiler. A specially crafted regular expression could let an unauthenticated attacker execute arbitrary code on the GitLab server — no login, no user interaction. It affects self-managed GitLab CE and EE versions all the way back to GitLab 7.0 (June 2014). Fixes landed in versions 19.5.1, 19.4.3 and 19.3.6, with backports down to 18.11.13; GitLab.com and GitLab Dedicated are already patched. The flaw was reported by researcher "joaxcar" through GitLab's HackerOne bug bounty — the same researcher who reported another critical RCE (CVE-2026-97229) just ten days earlier. Internet watchdog Shadowserver tracks more than 2,700 GitLab CE instances exposed online.

Why it matters

A self-hosted GitLab holds an organization's source code, secrets and deployment keys. A server takeover means credential theft and potential supply-chain attacks against everything that server builds. This is why maintenance is security, not housekeeping.

What it means for you

If you run self-managed GitLab, patch immediately — then rotate secrets and keys. Audit what else is internet-exposed. And if you sell development services, this is the case study for why maintenance retainers exist.
